## 一、为什么非要有它

整模块 `swiftc -typecheck` **抓不出**下面两类问题 —— 库内一切正常，只有**模块外**视角才能看见：

| 类别 | 症状 | 只有哪一关能抓 |
|---|---|---|
| 漏登记 conformance | `.fdy` 对整类值类型不可达（或静默桥接成 `FdyWrapper<NSString>`） | 跨模块 typecheck |
| 改名后外界写不出来 | 库内改名成功、编译全过，宿主侧旧写法失效 | 跨模块 typecheck |
| 下标 / API 二义性被真正消除 | 纸面推演说「已消除」，实际两条重载仍在竞争 | **反证探针**（期望报错） |
| 行为等价性 | 「改动等价」只是推导，没有运行期证据 | 双运行时行为探针 |

| ④ | 全量编译 | `zsh .build/structprobe/build.sh` | **0 error**（**必须**看 `check_errors` 的输出，别只看末尾「构建完成」） |
| ⑤ | 双运行时行为探针 | iOS 18.0 与 26.5 各跑一遍 `diff` | **55 行逐行一致**（= 54 条 `S*` 断言 + `DONE`；判定集**只取** `^S` 与 `DONE`，且**必须含 `DONE`**） |

**① 的「3 条主 warning」别用 `grep -c 'warning:'` 数** —— 它把诊断的缩进附注行一并计入，会得到 8。
构成：3 条 `UIButton` 传统 inset 属性废弃（`contentEdgeInsets` / `imageEdgeInsets` / `titleEdgeInsets`）；

**⑤ 的判定集必须排除 `DIAG*` 行**（2026-09-18 实测）。`DIAGa` 是**运行时私有 selector 清单**，随系统版本
**必然**变化 —— 同一个探针 iOS 18.0 报 `total=139`、26.5 报 `total=159`（26.5 多出
`__canPreventGestureRecognizer:` / `__requiresGestureRecognizerToFail:` / `_sendTouchesToComponentController:` 等）。
把整份输出丢进 `diff` 会得到**假差异**；只判 `^S` + `DONE` 才是 `IDENTICAL`。
`DIAGb`（ivar 类型编码 `@"NSMutableArray"`）在两端一致，可以留在判定集里。
**写探针诊断行时优先断言与版本无关的事实**（类型编码、布尔真值），不要断言数量。

**③ 的报错数别用 `grep -c 'error:'` 数**：它数的是「含该子串的行」，会把缩进附注行**和回显的源码行**一起算进去 ——
`bind_negative` 只有 1 条主诊断，但源码里写着 `Fail<String?, ProbeError>(error: .boom)`（自带 `error:` 字面），
于是数成 **3**。**正确口径**：`grep -cE '^[^ |]+\.swift:[0-9]+:[0-9]+: error:'`。
主诊断实测：`subscript_negative` **1 条**、`bind_negative` **1 条**；负向探针的通过条件是
**报出预期的那条诊断**，不是条数。

**① 别用 `xcodebuild`**（2026-09-18 实测）：本机沙箱下会直接失败 ——
`Could not resolve package dependencies: sandbox-exec: sandbox_apply: Operation not permitted`，
报的是依赖解析而非代码问题。① 只能走下面的 `swiftc -typecheck @files`。

## 四、`build.sh` 与 `Info.plist` 全文

```bash
#!/bin/zsh
# 构建 structprobe：把真实 Sources/Fdy 编成模拟器 dylib，再用探针 app 链接
# 用法：zsh .build/structprobe/build.sh
set -e
cd /Users/mac/workspace/demo/work-points/fdy-swift
SDK=$(xcrun --sdk iphonesimulator --show-sdk-path)
# ⚠️ 清单落 .build/，**不要写 /tmp** —— /tmp 会被系统整体清空
find Sources -name "*.swift" > .build/structprobe/files.txt

# 编译失败必须中止：`cmd 2>&1 | grep ... || true` 会把 swiftc 的退出码吞掉，
# 一旦有 error 仍会走到末尾打印「构建完成」，随后 run_both.sh 拿**旧二进制**跑出"假绿"。
# (2026-09-18 真实踩到：App.swift 插值括号不闭合，脚本却报构建完成。)
check_errors() {
    local log=$1 what=$2
    if grep -qE 'error:' "$log"; then
        echo "!!! $what 编译有 error，中止（用旧二进制跑判定会得到假结论）"
        exit 1
    fi
}

echo "--- 1/3 编译 Fdy dylib ---"
# -install_name 必须显式写成 @rpath/...，否则装进模拟器后会按编译时的相对路径找 dylib 而加载失败
xcrun swiftc -emit-library -emit-module -module-name Fdy \
    -target arm64-apple-ios18.0-simulator -sdk "$SDK" -swift-version 5 \
    @.build/structprobe/files.txt \
    -Xlinker -install_name -Xlinker @rpath/libFdy.dylib \
    -emit-module-path .build/structprobe/lib/Fdy.swiftmodule \
    -o .build/structprobe/lib/libFdy.dylib 2>&1 | grep -v "incompatible-sysroot" \
    | tee .build/structprobe/build_dylib.log || true
check_errors .build/structprobe/build_dylib.log "1/3 Fdy dylib"

echo "--- 2/3 编译探针 app ---"
xcrun swiftc -parse-as-library -target arm64-apple-ios18.0-simulator -sdk "$SDK" -swift-version 5 \
    -I .build/structprobe/lib -L .build/structprobe/lib -lFdy \
    -Xlinker -rpath -Xlinker @executable_path/Frameworks \
    .build/structprobe/App.swift -o .build/structprobe/Probe.app/Probe 2>&1 | grep -v "incompatible-sysroot" \
    | tee .build/structprobe/build_probe.log || true
check_errors .build/structprobe/build_probe.log "2/3 探针 app"

echo "--- 3/3 打包签名 ---"
cp .build/structprobe/lib/libFdy.dylib .build/structprobe/Probe.app/Frameworks/
cp .build/structprobe/Info.plist .build/structprobe/Probe.app/
codesign --force --sign - .build/structprobe/Probe.app/Frameworks/libFdy.dylib 2>&1 | tail -1
codesign --force --sign - .build/structprobe/Probe.app 2>&1 | tail -1
echo "构建完成"
```

`Info.plist` 要点（缺一不可）：

| 键 | 值 | 为什么 |
|---|---|---|
| `CFBundleIdentifier` | `com.wbtest.structprobe` | `simctl launch` 要用它 |
| `CFBundleExecutable` | `Probe` | 须与 `-o .../Probe` 输出名一致 |
| `MinimumOSVersion` | `18.0` | 与包门槛对齐 |
| `UILaunchScreen` | 空 `<dict/>` | **可省**。实测（2026-09-18）删掉它后 app 仍正常启动、41 行断言全出 —— 「缺它拒绝启动」的说法在本探针上不成立。保留只为与真机 / 上架要求对齐 |

## 五、短探针全文（这六份是持久副本）

### `subscript_probe.swift` —— 下标正向

```swift
import Fdy

// 正向：两条下标各司其职，不再靠上下文返回类型消解
func probeString(_ s: String) {
    // String 专有：安全子串（越界返回 nil）
    let _: String? = s[fdy_range: 0 ..< 2]
    // RRC 通用：切片
    let _: Substring = s[fdy_slice: 0 ..< 2]
}

func probeArray(_ a: [Int]) {
    let _: ArraySlice<Int> = a[fdy_slice: 1 ..< 3]
}

func probeMutate() {
    var array = [1, 2, 3, 4]
    array[fdy_slice: 1 ..< 3] = [9, 9]

    var str = "Hello"
    str[fdy_range: 0 ..< 5] = "Hi"
    str[fdy_slice: 0 ..< 2] = "Yo"
}

// String 的 NSRange 版仍用 fdy_range（NSRange 不是 RangeExpression，与切片版无冲突）
func probeNSRange(_ s: String) {
    let _: String? = s[fdy_range: NSRange(location: 1, length: 3)]
}
```

### `bind_probe.swift` —— `bind(from:)` 正向

```swift
import Combine
import Fdy
import UIKit

private final class ProbeVM {
    @Published var name: String?
    @Published var flag: Bool = false
}

@MainActor
func bindProbe() {
    let textField = UITextField()
    let label = UILabel()
    let switchView = UISwitch()
    let scrollView = UIScrollView()
    let vm = ProbeVM()

    // 1) 向后兼容：AnyPublisher 照旧可传
    let erased: AnyPublisher<String?, Never> = Just("a").eraseToAnyPublisher()
    textField.fdy_textPublisher.bind(from: erased)

    // 2) Subject —— 此前必须 .eraseToAnyPublisher()
    let subject = CurrentValueSubject<String?, Never>("b")
    label.fdy_textPublisher.bind(from: subject)

    // 3) Published.Publisher —— 此前必须 .eraseToAnyPublisher()
    textField.fdy_textPublisher.bind(from: vm.$name)

    // 4) 中间流（map + filter）—— 此前无 erase 根本编不过
    textField.fdy_textPublisher.bind(from: subject.map { $0?.uppercased() }.filter { _ in true })

    // 5) 库自有 FdyControlEvent，Output 匹配时**直接传**，连 map 都不用
    switchView.fdy_isOnPublisher.bind(from: scrollView.fdy_didEndDraggingWithDecelerationPublisher)

    // 6) FdyControlEvent 经 map 换 Output 后照样可传
    switchView.fdy_isOnPublisher.bind(from: textField.fdy_tapPublisher.map { _ in true })
}
```

### `bind_negative.swift` —— `bind(from:)` 反证

```swift
import Combine
import Fdy
import UIKit

// 反证：Failure 非 Never 的上游**必须**编不过。
// 若本文件编译通过，说明 bind(from:) 被放宽到了不该放宽的程度。
private enum ProbeError: Error { case boom }

@MainActor
func bindNegative() {
    let textField = UITextField()
    let failing = Fail<String?, ProbeError>(error: .boom)
    textField.fdy_textPublisher.bind(from: failing)
}
```

期望错误：`error: instance method 'bind(from:)' requires the types 'ProbeError' and 'Never' be equivalent`

> 两个负向探针的**主诊断各只有 1 条**（`subscript_negative` = `cannot convert value of type 'String?' to specified type 'Substring'`）。
> 数它们**别用 `grep -c 'error:'`** —— 本文件的 `Fail<String?, ProbeError>(error: .boom)` 自带 `error:` 字面，
> 被回显的源码行会被一起数进去，得到 3。用 §三 给的主诊断口径，并且**以「报出预期的那条」为通过条件**。

## 六、长探针的规格（无源码，需重写）

### `readme_probe.swift` —— README 全代码块重放

按 README **出现顺序**逐块重放 `swift` 代码块，要求跨模块 0 诊断。覆盖 `block 00` 与 `block 02`–`block 23`
（共 25 块；`block 01` 是 `Package.swift` 片段，非 Swift 源码，跳过）。

**改写原则（破坏它验证就失效）**：只补**最小上下文** —— 未定义符号 → 局部声明、伪代码 `...` → 真实表达式、
主线程入口 → `@MainActor`。**绝不改 API 调用形态**。
这份探针的价值就在于「README 里的写法**原样**能编过」，一旦顺手「修一下」就变成自欺。

### `conformance_probe.swift` —— 32 条 conformance 全覆盖

核心手法：**显式类型标注收口**，`let _: FdyWrapper<X> = x.fdy`。
只写 `let w = x.fdy` 是**没用的** —— 推断会跟着实际类型走，静默桥接了也看不出来（`String` → `NSString` 那种）。

必须覆盖三类边界：

1. 全部 32 条登记类型（清单见 `工业级_代码治理方案.md` §8.3 ① 或 README「协议」一节）
2. **CF 继承路径**：`CGPath` 显式登记 + `CGMutablePath` **不登记**，断言子类也能 `.fdy` 且能用父类链式方法
3. 嵌套泛型容器：如 `FdyWrapper<[String: [Int]]>`
4. `with` / `do` / `build` / `then` 四件套至少各一次

> 第 3 批新增的 3 条（`UIBackgroundConfiguration` / `UIListContentConfiguration` /
> `UIContentUnavailableConfiguration`）都是 **struct**，漏登记时的表现不是报错而是 `.fdy` 不可达 ——
> 所以这 3 条必须**显式标注**收口，标注失败才会报错。

| S28 | `UISegmentedControl` 改索引 → 库的 publisher 收到（走的是 **KVO 通道**）。`_setSelectedSegmentIndex:notify:true` 的 `events=0`，即 `notify:` **不发** `.valueChanged` —— 合并通道的设计恰好兜住这点 |

**S27–S29 的驱动方式都是私有 API,且都从「真实调用链的内部一环」发起,不是伪造事件** ——
`S27` 走 `UIStepper` 自己发事件的出口、`S28`/`S29` 走它的内部选中逻辑。
区分标准很简单:`stepper.sendActions(for: .valueChanged)` 那种「直接喂事件给订阅者」的写法**不算证据**。
唯一没被覆盖的是「手指触摸 → UIKit 发 `.valueChanged`」这一环,需要 XCUITest(本机无 `idb`/`fbsimctl`,
`simctl` 无触摸子命令,`osascript` 被 TCC 拒)。

**iOS 26.5 把 `UIStepper` 整个换成了 DesignLibrary 实现**
(`UIStepperDesignLibraryVisualElement` + `UICoreHostingView<DesignLibraryStepper>`,**没有** `_UIStepperButton`)。
本库只依赖 KVO 与 `.valueChanged`,不碰私有视图结构,所以不受影响 —— 但**任何**基于 `UIStepper` 私有子视图的
做法都会在 26.5 上失效。

**`DONE` 是判定集的一部分,不是装饰。** 探针中途抛 `NSException` 会**直接终止进程**,此时两份输出只是
「一致地没跑完」,`diff` 照样报一致。
2026-09-18 真实踩到一次:`stepper.stepValue = 0` 抛 `NSInvalidArgumentException: stepValue must be greater than 0`,
崩在 `S33`,两端同时缺 `DONE`,起初被误读成 43 行「通过」。
判据:抓取判定集**必须包含 `DONE`**,否则整个判定作废。

> **S40–S43 只打印布尔关系,不打印系统读回的原值** —— 原值依赖系统默认(18.0 / 26.5 可能不同),
> 混进判定集会让 `diff` 假报差异,与 `DIAGk` 同一类坑。
>
> 另:`IDENTICAL` 只证明两运行时**一致**,**不证明断言为真** —— 每次加了新断言都要单独核一遍
> 布尔值(第 3 批 11 个布尔在两运行时全为 `true`)。

**`DIAGk`（不进判定集）**：`separatorInset` 的读回值被 UIKit 自行校正,且**规则随系统版本变** ——
`left` 传 `16` 读回 `24`（18.0 / 26.5 一致），`right` 传 `8` 在 18.0 读回 `8.0`、在 26.5 读回 `16.0`。
凡此类「被系统改写的量」一律用 `DIAG` 前缀输出，否则 ⑤ 会因系统差异**假报失败**。

**S21 必须让 runloop 转圈再读**（`RunLoop.main.run(until: Date().addingTimeInterval(0.2))`）：
UIKit 的 configuration → titleLabel 桥接是**异步**的，立刻读会得到假 `nil`。

**S23c 的触发方式**：`scrollView.delegate?.scrollViewDidEndDragging?(scrollView, willDecelerate: true)`
—— 直接调 delegate 方法即可，无需真的触摸。

## 八、工具级坑（都踩过，别再试）

- **模拟器处于 Shutdown 时 `simctl install` 直接失败** → 输出文件为空 → `diff` 得到**假 IDENTICAL**。
  必须 `boot` + `bootstatus -b`，且判定一致性前**校验行数非零**。
- **探针 app 是常驻 `UIApplication`，`--console-pty` 不会自己退出** —— 必须后台起 + 定时 `kill`，
  否则一直挂到工具超时（会被误判成构建失败）。
- **别把任何中间产物写 `/tmp`** —— 会被系统整体清空（本脚手架的历史探针已蒸发过一次）。
- **`grep -c 'warning:'` 会把诊断的缩进附注行一起数进去** —— 4 条主诊断数成 8。
  判基线漂移看 `grep -E 'warning:' | sed -E 's/^[^ ]+:[0-9]+:[0-9]+: //' | sort -u`。
- **macOS BSD grep 的 BRE 不支持 `\|`，也不支持 `\s`** —— `grep -n 'a\|b'` **静默当字面量**返回空。
  **一律 `grep -E`**，空白类写 `[[:space:]]`。
- **跨模块探针报满屏 `cannot find type` 时先看有没有 `import Fdy`** —— 那是假阴性，不是 API 不可达。
- **`swiftc` 整模块 typecheck 抓不出漏登记 conformance** —— 必须走 §三 的 ③。
- **`api_coverage.sh` 报的「未见同名链式」会因「一个 header 声明多个类」而误报**（第 3 批踩到）：
  `UITabBarAppearance.h` 里同时有 `UITabBarItemAppearance` / `UITabBarItemStateAppearance`，
  脚本按文件取属性，于是把**别的类**的 7 个属性（`badgeBackgroundColor` / `iconColor` …）算成缺口；
  `UIListContentConfiguration.h` 里的 `UIListView.configuration` 同理。
  **报「未见」≠ 真有缺口，必须人眼归属到类。**
- **探针里把多个链式方法串成一条表达式再加 `print("a\(x)" + "b\(y)")` 会让编译器超时**
  （`unable to type-check this expression in reasonable time`，第 3 批踩到）：
  拆成「先算布尔/值到局部变量，再拼一行 `print`」即解。
- **`.fdy` 链式在探针里同样受 Swift 变量作用域约束** —— 局部变量重名会报
  `invalid redeclaration`，而 `build.sh` 的 `check_errors` 会当场拦下（这是它的预期行为，别绕过）。
