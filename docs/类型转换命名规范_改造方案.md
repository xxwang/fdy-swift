# 类型转换方法命名规范 · 改造方案

> 状态：**待审核**。审核通过后按 §七 的 6 个批次执行。
> 依据：全部结论来自本机实测（扫描脚本见 §十），无一条凭文档推断。
>
> **v2 变更（2026-09-18 二次拍板）**：**类型前缀一律保留**（v1 曾收窄为「UI/CG/CA 剥、NS 留」）。
> 规则因此退化为**纯机械规则**：新名 = `fdy_to` + 返回类型原名，**零消歧决策**。

---

## 一、决策记录

1. **动词统一 `to`** —— 全库不再出现 `as`（现存的 `fdy_asCurrency` 一并改）。
2. **类型前缀一律保留** —— UI / NS / CG / CA / CI **全部保留，不做任何剥离**。
   - 例：`fdy_toUIImage()` / `fdy_toCGPoint()` / `fdy_toNSRange()` / `fdy_toCACornerMask()`。
   - 与 v1 相比的好处：**只有一套规则**，不需要「哪些前缀剥、哪些留」的例外表；
     且 `NSRange.fdy_toRange(in:)` ↔ `Range.fdy_toNSRange(in:)` 天然形成一对**对称自解释**的双向转换。

## 三、前缀保留的依据（含 v1 剥离方案的反向证据，留档）

### 3.1 剥掉 UI / CG / CA —— 实测确实零冲突，但**没有收益**

| 前缀 | 剥后短名样例 | 冲突 |
|---|---|---|
| `UI` | `UIImage`→`Image`、`UIColor`→`Color`、`UIRectCorner`→`RectCorner` | 无 |
| `CG` | `CGPoint`→`Point`、`CGSize`→`Size`、`CGPath`→`Path` | 无 |
| `CA` | `CATransform3D`→`Transform3D`、`CACornerMask`→`CornerMask` | 无 |

不冲突，但**换不来任何东西**，反而：① 同库内出现两套规则（剥 / 不剥）；② `toImage` / `toColor` 会与
SwiftUI 的 `Image` / `Color` 产生阅读联想，而本库是 UIKit 库；③ 与 Apple 自身习惯相悖
（`CGPoint`、`CGRectMake` 从不缩）。

### 3.2 剥掉 NS —— **硬撞，7 个里 5 个**

| 剥掉后的名 | 接收者 | 实际返回 | 撞上的真类型 |
|---|---|---|---|
| `toString()` | `String` | `NSString` | `String` —— 在 String 自己身上叫 `toString`，语义荒谬 |
| `toArray()` | `Array` | `NSArray` | `Array` —— 同上 |
| `toRange(...)` | `String` / `NSAttributedString` | `NSRange` | `Range`（标准库泛型） |
| `toAttributedString()` | `String` / `NSMutableAttributedString` | `NSAttributedString` | `AttributedString`（Foundation，Swift 5.5+，**另一套并存 API**） |
| `toMutableAttributedString()` | `NSAttributedString` | `NSMutableAttributedString` | 与上条成对，需同进同退 |
| `toNumber()` | `BinaryInteger` 等 | `NSNumber` | 无同名类型，但与同库 `toDecimal` / `toInt` / `toDouble` 区分度骤降 |
| `toDecimalNumber()` | 同上 | `NSDecimalNumber` | 与 `toDecimal` 只差一个后缀，极易看错 |

**结论：前缀一律保留。** 依据有两条：

1. `NS` 是 ObjC 桥接类型**正式名的一部分**，Apple 自己从不缩（`NSStringFromClass`、`NSValue`、`NSRange`）。
2. 剥掉后的混淆不是「风格问题」而是「**指向错误类型**」—— `NSAttributedString` 与 `AttributedString`
   是 Foundation 里两套并存的 API，名字撞上会实打实误导。

## 五、不改（边界清单，共 17 处）

| 类 | 符号 | 理由 |
|---|---|---|
| 已合规（3） | `Array.fdy_toNSArray()`、`Range<String.Index>.fdy_toNSRange(in:)`、`CGAffineTransform.fdy_toCATransform3D()` | 命名已达标 |
| static 工厂（2） | `Date.fdy_date(from:)`、`Date.fdy_string(from:format:)` | 时间戳**解析**，接收者是 `Date.Type`；改成 `fdy_toDate(from:)` 自相矛盾 |
| static 取值（7） | `Date.fdy_random()` ×4、`fdy_nowSecond()`、`fdy_nowMillisecond()`、`fdy_daysInMonth(...)` | 不是类型转换，名字也不是类型名 |
| 区间构造（2） | `BinaryInteger.fdy_range(from:)` / `(to:)` | 返回 `CountableRange<Int>`，是构造不是转换；与 `NSRange.fdy_range(in:)` 同名不同义 —— 后者改名后撞名自动消除 |
| 语义化名（1） | `SignedInteger.fdy_toRomanNumeral()` | 名字已达标，且返回值（`String?`）不是名字所指类型 |
| **同名异义·语义非转换（2）** | `String.fdy_Character(at:)`（返回 **`String`** —— 截取第 n 个字符）、`NSNumber.fdy_Decimal(groupingSeparator:…)`（返回 **`String?`** —— 数字格式化） | 它们与被改名的那一族**同名但语义完全不同**。⚠️ 本条是**执行阶段实测补录**：初版清单漏了它们，`calls`（按名字聚合）据此误判、改错 2 处，靠 typecheck 才抓回（见 §十一） |

另有两类**不在本次范围**：

- **计算属性** `Collection.fdy_range`（`Range<Index>` 索引范围读取）—— 不是 `func`，脚本本就不收。
- **格式化 / 编码 / 截取 / 派生**（`fdy_hexString`、`fdy_rGBInt`、`fdy_jpegBase64String`、`fdy_subData`、`fdy_ranges(of:)` …）
  —— 名字里的限定词（`hex` / `rGB` / `base64` / `sub`）才是信息量所在，加 `to` 反而失真。

## 六、三个小项（已按推荐执行）

> 用户指示「按你方案执行」= 三项全部采纳**推荐**列，已落地。

| # | 项 | 采纳 | 备选（未采纳） |
|---|---|---|---|
| 1 | `Encodable.fdy_string(format:)` | **`fdy_toJSONString(format:)`** —— `JSONEncoder` 产物，且同库另有 7 个 `toString`，不加限定词无法区分 | `fdy_toString(format:)` 机械合规 |
| 2 | `Array` / `Dictionary.fdy_Data()` | **`fdy_toJSONData()`** —— `JSONSerialization` 产物；而同库 `String.fdy_Data()` 是 UTF-8 编码，都叫 `toData` 会混 | `fdy_toData()` 机械合规 |
| 3 | `fdy_GetAO` / `fdy_SetAO` | 本次**不动**（不属类型转换） | 一并归一为 `fdy_getAssociatedObject` / `fdy_setAssociatedObject`（+20 处调用） |

> `Date.fdy_string(_:locale:timeZone:)` 与 `String.fdy_Characters()` 在 v1 里是决策项，**v2 已被规则自动决定** ——
> 前者 → `fdy_toString(_:locale:timeZone:)`（与 `String.fdy_toDate(format:)` 对称），后者 → `fdy_toCharacters()`
> （返回 `[Character]`，机械规则算不出合法名，属手工补录）。

两个**顺手发现、不建议本次动**的问题，记录备查：

- `Dictionary.fdy_Data()` 里 `assertionFailure("data requires Key == String")` 是**硬编码英文**，与全库中文注释风格不一致。
- `Encodable.fdy_string(format isFormat: Bool = false)` 的外部标签 `format` + 内部名 `isFormat` 表达的是
  **「是否 prettyPrinted（缩进 + 排序）」**，命名误导；若采纳 §六-1，可顺势把标签改成 `prettyPrinted`。

每批**只改定义 + 该文件内的调用点**，改完立刻跑第 ① 道 typecheck —— 漏改的调用点会即刻报错，这是最有效的守门。

### ⛔ 执行纪律：**禁止全库替换**（本次最危险的一步）

有 **3 个同名符号只有部分定义要改**，`sed -i 's/fdy_string/fdy_toJSONString/g'` 这类操作**必然误伤**：

| 符号 | 要改 | ⛔ 不改 |
|---|---|---|
| `fdy_string` | `Data++.swift:139`、`Date++.swift:222`、`Codable++.swift:15` | `Date++.swift:443`（static 工厂） |
| `fdy_date` | `BinaryInteger++.swift:154`、`DateComponents++.swift:13`、`String+DateFormatting.swift:11` | `Date++.swift:425`（static 工厂） |
| `fdy_range` | `NSRange++.swift:30` | `BinaryInteger++.swift:206`、`:219`（区间构造） |

还有 **2 个同名多义**（同一旧名映射到**不同**新名）：

| 符号 | 映射 A | 映射 B |
|---|---|---|
| `fdy_Data` | `String` → `fdy_toData` | `Array` / `Dictionary` → `fdy_toJSONData` |
| `fdy_string` | `Data` / `Date` → `fdy_toString` | `Encodable` → `fdy_toJSONString` |

**因此：必须按 `rename_map.json` 的「文件:行」逐点改，不许按符号名替换。**

其他项目现存教训：

- `Edit` 静默失效已踩过；**同一文件必须串行改，改完逐个回读复核**。
- 批 6 的 13 处注释示例里，`Collection++.swift:12` 那条属**另一个** `fdy_range`（计算属性），不能跟着改。

### 11.2 实测踩坑：`calls` 按名字聚合，天然区分不了同名重载

方案 §七 预警过「同名多义」，但只列了 3 组（`fdy_string` / `fdy_date` / `fdy_range`）。
执行时 **typecheck 又抓出 2 组漏网的**，且都是**同接收者同名、仅参数不同**，`calls` 的口径看不出来：

| 误判点 | 我当时的推断 | 真相 | 后果 |
|---|---|---|---|
| `NSNumber++.swift:78` `self.fdy_Decimal(minimumFractionDigits:…)` | 调 `BinaryInteger`/`String` 的转换版（→ `fdy_toDecimal`） | 调**本文件 `:13`** 的 `NSNumber.fdy_Decimal(groupingSeparator:…) -> String?`（**格式化**） | typecheck：`value of type 'NSNumber' has no member 'fdy_toDecimal'` |
| `String+Validation.swift:103` `self.fdy_Character(at: i)` | 调 `String+Conversion.swift:48` 的转换版（→ `fdy_toCharacter`） | 调 **`String+Range.swift:206`** 的 `fdy_Character(at:) -> String`（**截取**，返回 String 不是 Character） | typecheck：`cannot convert value of type 'Character?' to expected argument type 'String'` |

两处均已回滚，`apply_rename.py` 里就地写了 ⛔ 注释说明为何排除。
**教训**：`calls` 只能回答「这个名字被调了几次」，回答不了「调的是哪个重载」——
只有 typecheck 能兜住这类错。

补做的排查工具：`.build/structprobe/check_reloads2.py`（**时序无关**口径：以 `rename_map.json` 为基准，
找「改名后旧名仍有同族定义留存」的组）。实测全库共 5 个部分改名组，除上述 2 个外，
另 3 个（`fdy_date` / `fdy_string` / `fdy_range`）是方案 §五 白名单里已列明的刻意保留。

> 第一版 `check_reloads.py` 走的是**改名之后**扫磁盘的口径 —— 那时「已改名的兄弟」已不叫旧名，
> 拿不到对比组，**假报「(无)」**。工具本身也会踩时序坑，已废弃。
