# 项目结构 · 命名 审计与优化方案

> 审计范围：`Sources/Fdy`（252 个 `.swift`、32071 行）+ `Package.swift` + `README.md` + `docs/`。
> 方法：全量 `find` + `grep` 事实核验，**每条结论附 `文件:行号`**，无一条靠推断。
> 状态：**源码一行未动**，本文只出方案。

## 一、一句话结论

**主体架构是健康的**——`Core/{Chain, Common, Components, Extensions, Protocols, Wrapper}` 六分法职责清晰，
`Extensions/` 侧 763 个方法 **100% 遵守 `fdy_` 前缀**（违规 0 条），`Chain/` 侧 **0 条 `fdy_` 混入**，
`Logger/` 6 个文件与类型名 1:1 对齐。这些是扎实的部分。

问题集中在三个面：**命名有 9 处硬伤**（其中 3 处是全库唯一的例外，改起来无风险）、
**文件后缀风格有 5 种并存**（140 个 Extensions 文件里 106 标准 + 34 例外）、
**10 处 `@available` 在平台底线已提到 iOS 18 后变成死标注**。

## 三、A 组：命名硬伤（9 条，无争议，改动小）

### A1 `LocationFdyPermissionType` —— `Fdy` 跑到词中间

- 现状：`Common/FdyPermissionChecker.swift:54` `public enum LocationFdyPermissionType`
- 全库唯一一例「前缀不在词首」。
- 它已是 `FdyPermissionType` 的嵌套类型（`:37`），外层已带前缀，内层再加是**双重前缀**。
- 建议：内层改 `Location`（调用侧变 `FdyPermissionType.location(.whenInUse)`），
  若要保留外部可直接书写的名字，另在 `FdyTypealias.swift` 加
  `public typealias FdyLocationPermissionType = FdyPermissionType.Location`。

### A2 `FdyHaptic.FdyFeedback` —— 嵌套内冗余前缀

- 现状：`Common/FdyHaptic.swift:8` `public enum FdyFeedback`，外层是 `FdyHaptic`（`:6`）。
- 建议：`Feedback`，调用侧 `FdyHaptic.Feedback.impact(.light)`。

### A3 `ControlEvent` / `ControlProperty` 是 public 却无 `Fdy` 前缀

- 现状：`Combine/ControlEvent+Combine++.swift:17`、`Combine/ControlProperty+Combine++.swift:30`，
  两者均 `public struct`。
- **全库仅有的两个无 `Fdy` 前缀的公开类型**（名字直接沿用 RxSwift）。
- 与第三方库重名风险实存；也破坏「公开类型一律 `Fdy` 前缀」的可检索性。
- 建议：`FdyControlEvent` / `FdyControlProperty`。

### A4 `FdyDataStoreWrapper.swift` 里的类型叫 `FdyDataStore`

- 现状：`Wrapper/FdyDataStoreWrapper.swift:10` `@propertyWrapper public struct FdyDataStore<T>`。
- 文件名的 `Wrapper` 是冗余后缀（`@propertyWrapper` 已表达该语义），且与类型名不符。
- 建议：文件改名 `FdyDataStore.swift`。

### A5 `String++.swift` 里装的是 `FdyFont`，与 String 无关

- 现状：`Extensions/Stdlib/String/String++.swift:10` `public typealias FdyFont = UIFont`（`:16` 为 AppKit 分支）。
- 文件名为 `String++`，内容却是字体类型别名 + 5 个 `import`——**内容与文件名完全不符**。
- 建议：typealias 移到 `Common/FdyTypealias.swift`；该文件若仅剩 import，可整体删除
  （`import` 是文件级的，`Stdlib/String/` 其它文件各自已 import 所需框架）。

### A6 `Combine/Internals.swift` 是该目录唯一的风格例外

- 现状：13 个文件里 12 个叫 `X+Combine++.swift`，只有 `Internals.swift` 无任何后缀、无 `Fdy` 前缀
  （内含 `ClosureTarget` / `ControlEventSubscription` / `SubscribePublisher` 三个 internal 类型，`:9/:31/:82`）。
- 建议：改名 `Combine+Internals.swift`，内部三个 internal 类型建议加 `Fdy` 前缀（internal 虽不导出，
  但 `ControlEventSubscription` 与 A3 的 `ControlEvent` 家族重名会干扰检索）。

### A7 `UIButton+Chain.swift` 的 `backgroundImage` 重载语义差太远

- 现状：`UIButton+Chain.swift:230` `backgroundImage(_ image: UIImage?, for:)` 与
  `:250` `backgroundImage(_ color: UIColor, for:)` —— 同名重载，一个设图片、一个设纯色。
- `UIColor` 版本**方法名与行为不符**（那不是 image）。
- 建议：`UIColor` 版本改名 `backgroundColor(_:for:)`，与同文件 `:270` 的无状态版 `backgroundColor(_:)` 成对。

### A8 `isPointerInteractionEnabled` 的参数名不等于属性名

- 现状：`UIButton+Chain.swift:107` `func isPointerInteractionEnabled(_ isEnabled: Bool)`。
- 同目录所有其它方法都是「方法名 = 参数名」（`isEnabled(_ isEnabled:)`、`isSelected(_ isSelected:)` …）。
- 建议：参数名改 `isPointerInteractionEnabled`。
- 同类还有 `:116` `pointerStyleProvider(_ provider:)`（属性名是 `pointerStyleProvider`）。

### A9 README 目录结构写了一棵不存在的树

- 现状：`README.md:632` `│   └── Core.swift` —— **`Sources/Fdy/Core.swift` 不存在**（`ls` 报 No such file）。
- 同段落 `README.md:631` 把 `Wrapper/` 描述成 `@FdyDataStore`，与 A4 的文件名问题相关。
- 建议：删掉 `Core.swift` 一行；`Wrapper/` 描述随 A4 一并对齐。

## 四、B 组：目录结构（6 条，影响面大，需拍板）

### B1 `Combine/` 与 `Logger/` 与 `Core/` 平级，结构不自洽

```
Sources/Fdy/
├── Fdy.swift
├── Core/        ← 六分法
│   ├── Chain  Common  Components  Extensions  Protocols  Wrapper
├── Combine/     ← 为什么不在 Core 下？
└── Logger/      ← 为什么不在 Core 下？
```

- 若 `Core` 的语义是「核心能力」，`Combine`（事件绑定）与 `Logger`（日志）同样是核心能力，没有外置的理由。
- 两种自洽方案，二选一：
  - **方案 1**：`Combine/` → `Core/Combine/`、`Logger/` → `Core/Logger/`，保留 `Core` 这一层。
  - **方案 2（最终采纳）**：拆掉 `Core/` 这层，各能力目录全部平铺到 `Sources/Fdy/` 下。
- **决策（2026-09-17，用户拍板）**：采纳方案 2。理由 —— 把 `Combine` / `Logger` 收进 `Core` 之后，
  `Sources/Fdy/` 下只剩 `Core/` 一个目录，这层就成了纯冗余；两种方案都是纯 `git mv`
  （`Package.swift` 用 `path: "Sources/Fdy"` 整目标包含，零构建配置改动），故选层数更少的。

### B2 `Extensions/Protocols/` 与 `Protocols/` 同名不同义

| 路径 | 文件数 | 实际含义 |
|---|---|---|
| `Protocols/` | 4 | **本库自己的协议**：`FdyExtension` / `FdyLoadable` / `FdyReusable` / `FdySetupable` |
| `Extensions/Protocols/` | 12 | **Swift 标准库协议的扩展**：`Collection` / `Sequence` / `Comparable` … |

- 两个都叫 `Protocols`，语义相反，是这个结构里最容易误判的地方。
- 建议：`Extensions/Protocols/` → `Extensions/StdlibProtocols/`
  （与已有的 `Extensions/Stdlib/` 命名成体系）。

### B3 `Wrapper/` 是单文件目录

- 现状：只有 `FdyDataStoreWrapper.swift`（131 行）。
- 建议：并入 `Common/`（`@propertyWrapper` 本质是工具），或改名为 `PropertyWrapper/` 以正名。
  若预期后续会加更多 wrapper，保留目录也合理——**需拍板**。

### B4 `FdySkinable` 协议放错了目录

- 现状：`Common/FdySkinManager.swift:4` 定义 `public protocol FdySkinable`；
  而全库其余 4 个协议都在 `Protocols/`。
- 建议：`FdySkinable` 移到 `Protocols/FdySkinable.swift`，
  `FdySkinManager` 留在 `Common/`（它是工具类）。

### B5 `FdyAppearance` 与 `FdySkinManager` 概念重叠

| 类型 | 位置 | 职责 | 实现方式 |
|---|---|---|---|
| `FdyAppearance` | `Common/FdyAppearance.swift:4` | 全局 UI 外观（导航栏/标签栏/表格/滚动） | `UIAppearance` 代理，一次性 `initGlobalUI()` |
| `FdySkinManager` | `Common/FdySkinManager.swift:21` | 主题皮肤切换 | 观察者集合 `NSHashTable` + `updateSkin()` 广播 |

- 两者都管「全局外观」，一个走 `UIAppearance` 静态代理、一个走运行时观察者广播，**使用者不知道该用哪个**。
- 建议：明确边界并写进 README——`FdyAppearance` 只管「App 启动时的一次性默认样式」，
  `FdySkinManager` 只管「运行期主题切换」；或把 `FdyAppearance` 的样式装配也改成 `FdySkinable` 观察者。
- 另注：`FdySkinManager` 49 行，仅 `register` / `remove` / `updateSkin` 三个方法，功能极薄——**需拍板是否合并**。

### B6 `fdyG` 只收录了 7 个单例，另有 4 个同构单例没进去

- `fdyG` 收录：`helper` / `perChecker` / `queue` / `screen` / `symbol` / `path` / `haptic`（`FdyGlobal.swift:20-52`）。
- 未收录但同样 `static let shared` 的：`FdyAppearance`、`FdyPlist`、`FdyScreenCaptureMonitor`、`FdySkinManager`。
- 使用者要记「哪些能走 `fdyG.`、哪些要写 `Xxx.shared`」，无规律可循。
- 建议：全部收进 `fdyG`，或在 README 注明入选标准（例如「无状态工具走 `fdyG`，有状态管理器走 `.shared`」）。

## 五、C 组：文件命名后缀有 5 种风格

| # | 风格 | 数量 | 示例 | 分布 |
|---|---|---|---|---|
| 1 | `X++.swift` | **106** | `UIButton++.swift` | Extensions 主体 |
| 2 | `X+Word++.swift` | 3 | `UIView+Layout++.swift`、`UIView+Effects++.swift`、`CALayer+Animation++.swift` | Extensions/UIKit/UIView、Extensions/QuartzCore |
| 3 | `X+Word.swift` | 31 | 30 个 `String+*.swift` + `UIImage+Draw.swift` | Extensions/Stdlib/String（30）、Extensions/UIKit（1） |
| 4 | `X+Chain.swift` | 69 | `UIButton+Chain.swift` | Chain 全目录 |
| 5 | `X+Combine++.swift` | 12 | `UIControl+Combine++.swift` | Combine（+ `Internals.swift` 例外） |

**规律是「目录内部一致、跨目录不一致」**：`Stdlib/String/` 30 个文件全部用风格 3，`Chain/` 全部用风格 4。
唯独 `Extensions/UIKit/UIView/` 的 3 个文件是 **风格 1 + 风格 2 混用**：

```
Extensions/UIKit/UIView/UIView++.swift           ← 风格 1
Extensions/UIKit/UIView/UIView+Effects++.swift   ← 风格 2
Extensions/UIKit/UIView/UIView+Layout++.swift    ← 风格 2
```

以及 `Extensions/UIKit/` 下 `UIImage+Draw.swift` 是风格 3，而同级 `UIImage++.swift` 是风格 1。

**建议（需拍板选一个方向）**：

- **方向 A（推荐，改动最小）**：统一为「主类型用 `X++`，专题用 `X+Word`，不带第二个 `++`」。
  即只收拾 3 个风格 2 文件 → `UIView+Effects.swift` / `UIView+Layout.swift` / `CALayer+Animation.swift`；
  `Combine` 的 12 个 `+Combine++` 同步简化为 `+Combine`。改动 15 个文件名，零代码改动。
- **方向 B（彻底）**：全库统一 `X+领域.swift`（`UIButton+Chain.swift`、`UIButton+Combine.swift`、
  `UIButton+Extension.swift`），放弃 `++`。改动 178 个文件，README 与 docs 需同步。

### D2 `FdyModel1...FdyModel5` 命名含糊

- 现状：`Common/FdyModels.swift:3/11/21/33/47`，五个泛型元组容器。
- 问题一：`FdyModel1<A>` 只包一个值，**语义等价于 `A` 本身**，无使用价值。
- 问题二：`Model` 一词在本库已指「数据模型」，而这批类型是**元组容器**，语义冲突。
- 建议：改 `FdyTuple2...FdyTuple5`（与 Swift 标准库 `Zip2Sequence` 命名同族），删掉 `FdyModel1`。
  若旧名要保兼容，加 deprecated typealias 过渡。

### D3 `FdyAction*` 与 `FdyFunc*` 两套别名语义重叠

```
FdyAction       () -> Void          FdyFunc<R>        () -> R
FdyAction1<A>   (A) -> Void         FdyFunc1<A, R>    (A) -> R
FdyAction2<A,B> (A,B) -> Void       FdyFunc2<A,B,R>   (A,B) -> R
...                                  ...
FdyAction5<A..E>  (A..E) -> Void    FdyFunc5<A..E,R>  (A..E) -> R
```

- `FdyAction5<A,B,C,D,E>` **就是** `FdyFunc5<A,B,C,D,E,Void>` 的展开——12 个别名里有 6 对是重复语义。
- 建议二选一：
  - 保留两套，但把 `FdyAction*` 改成 `FdyFunc*` 的 `Void` 特化别名
    （`public typealias FdyAction5<A,B,C,D,E> = FdyFunc5<A,B,C,D,E,Void>`），语义关系显式化；
  - 或直接砍掉 `FdyFunc*`，只留 `FdyAction*`（本库实际用到返回值的场景少，需先 grep 使用面）。
- 命名本身也不平行：一套带尾数字（`FdyFunc1`），零元那套不带（`FdyFunc`），但 `FdyAction` 只有零元才不带。

### D6 `FdyButton` 与 `FdyTextView` 的类约定不一致

### D7 `FdyWrapper` 的 `NSObject` 空扩展 vs 内联 conformance，两种做法并存

- 做法一：单独开文件写 conformance + 空壳扩展
  `Chain/Foundation/NSObject+Chain.swift:3` `extension NSObject: FdyExtension {}`

- 做法二：写在首个使用文件头部

- 两种都能跑，但读代码的人要找 `FdyExtension` 的 conformance 全表就得两处翻。
- 建议：统一为做法二（内联在首个使用文件顶部），删掉 `NSObject+Chain.swift` 的空壳扩展——
  但注意这个文件同时是 `NSObject` conformance 的**唯一登记处**，删前需确认没有别的地方依赖它的存在。
- 全库 conformance 共 3 条：`NSObject`、`Date`（`Chain/Foundation/Date+Chain.swift`）、`UIButton.Configuration`。

### 9.2 执行中新发现并修掉的两处

1. **类工厂返回类型写死** → `FdyButton.button()` 原本返回 `FdyButton`、`FdyTextView.textView()` 返回 `FdyTextView`，
