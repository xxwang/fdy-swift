# 工业级代码治理方案

> **目标**：让 `fdy-swift` 可被**任意 iOS 项目信任接入** —— 不污染宿主命名空间、语义与命名一致、
> 无「看着能用其实用不了」的 API、边界输入不崩、并发契约明确。
>
> **基线**：分支 `Swift6`，起点提交 `7e8b14d`，`Sources/Fdy` **253 文件 / 32086 行**。
>
> **方法**：四路并行**只读**审计（`Chain/` · `Extensions/` · `Common+Combine+Logger+Protocols+Components` ·
> 链式覆盖专项）+ 编译级实测（整模块 typecheck / 跨模块 typecheck）+ 运行期双运行时行为探针。
> 每条结论附 `文件:行号`；凡未经实测的一律显式标注「未验证」。

## 三、本轮已落地（无风险项，四道验证已过）

### 3.1 修复 34 个「写好了但对外不可达」的链式方法

**缺陷**：`FdyWrapper.init` 是 internal（`Protocols/FdyExtension.swift:31`），模块外无法手工构造 wrapper。
所以类型必须自己 conform `FdyExtension` 才能拿到 `.fdy`。而下面 3 个类型的 Chain 文件**漏了登记**：

| 文件 | 方法数 | 类型性质 |
|---|---:|---|
| `Chain/UIGeometry/UIEdgeInsets+Chain.swift` | 6 | struct |
| `Chain/Foundation/DateComponents+Chain.swift` | 15 | struct |
| `Chain/CoreGraphics/CGMutablePath+Chain.swift` | 13 | Core Foundation 类型 |

**编译级证据**（跨模块 `-typecheck`，`-I .build/structprobe/lib`）：

```
error: value of type 'UIEdgeInsets' has no member 'fdy'
error: value of type 'DateComponents' has no member 'fdy'
error: value of type 'CGMutablePath' has no member 'fdy'
error: 'FdyWrapper<Base>' initializer is inaccessible due to 'internal' protection level
```

**修法**：各文件顶部补一行 conformance（与 `NSObject+Chain.swift:8` 的登记约定一致）。

> ⚠️ 过程中修正了一处**我自己的误判**：最初按「`Base ==` 约束即值类型」筛，把
> `UIImage.SymbolConfiguration` 判为不可达。实测它是 `NSObject` 子类、**继承可达**；
> 真正漏掉的是 `CGMutablePath`。**结论以编译器为准，不以模式匹配为准。**

### 3.2 修复 `String` 的静默类型错误

漏登记 conformance 时，`"abc".fdy` **不会编译失败**，而是经 `NSString` 桥接解析成 `FdyWrapper<NSString>`：

```
error: 'String._ObjectiveCType' (aka 'NSString') is not implicitly convertible to 'String'
```

即调用方以为在链式配置 `String`，`.build()` 却返回 `NSString`。这是比「缺 API」更危险的形态。
新增 `Chain/Stdlib/String+Chain.swift`：只放 conformance + 一段「为何不提供链式 setter」的说明
（`String` 系统 API 已足够完整，库内另有 176 个 `fdy_` 方法，再加链式只会造出第二套入口）。

### 3.3 修复 3 个必崩路径

`Extensions/Stdlib/String/String+Range.swift` 的三个方法在**构造 `Range` 时**就 trap
（`fdy_slice` 自身的 `guard` 根本来不及执行），与注释承诺的「越界返回空字符串」矛盾：

| 方法 | 原写法 | 触发例 |
|---|---|---|
| `fdy_substring(from:)` | `from ..< utf16.count` | `"abc".fdy_substring(from: 10)` → `10..<3` **trap** |
| `fdy_substring(from:length:)` | `start` 只夹下界 | `from: 10, length: 1` → `10..<3` **trap** |
| `fdy_substring(from:to:)` | `start` 只夹下界 | `(100, 200)` → `100..<3` **trap** |
| `fdy_Character(at:)` | 继承上一条 | `"abc".fdy_Character(at: 99)` **trap** |

**修法**：`start` 一律夹到 `[0, utf16.count]`。**只影响原本就 trap 的输入**，正常路径逐位不变
（探针 `S16`：`normal=[bc]` 与修复前一致）。

### B1 命名空间污染 —— 头号阻塞（建议最先处理）

**问题**：库把大量符号铺进了宿主的**全局命名空间**，宿主或第三方库只要定义了同名符号，
**编译期直接失败**（`invalid redeclaration` / `ambiguous operator`）。

| 类别 | 数量 | 代表 |
|---|---:|---|
| 运算符重载 | **52 个** static 运算符方法 | `CGPoint + - * /`、`CGSize + - * /`、`CGVector`（共 31 个位置运算）、`Dictionary + += - -=`、`String * Int`、`NSAttributedString + +=`、`UIEdgeInsets + +=`、`NSPredicate ! + |`、`Optional == !=` |
| 自定义运算符 | **3 个** + 1 个 `precedencegroup` | `?=`、`??=`、`=~`（含全局 `RegPrecedence`） |
| 无前缀公开 `init` / `subscript` | **约 52 处** | `UIColor(hex:)`、`UIImage(color:)`、`Array[safe:]`、`Dictionary[safe:]`、`String[nsRange:]`、`CGRect(x:y:width:height:)` 便利构造… |

**具体风险点**（实测/推理）：
- `CGPoint * CGFloat` 这类是宿主 App 与图形库**最常自建**的扩展，撞名概率极高；即便不撞名，也会**悄悄改变宿主内重载解析结果**。
- `Dictionary` 的 `+ - += -=` 是 stdlib **刻意不提供**的，`-` 的 rhs 是 `some Sequence<Key>`，覆盖面极广。
- `Array++.swift:8` 与 `StdlibProtocols/BidirectionalCollection++.swift:20` 有**两个同名 `subscript(safe:)`** 且语义不同（Array 版不支持负数，协议版 `-1` 取尾）——`arr[safe: -1]` 的结果**取决于静态类型**。
- `RangeReplaceableCollection++.swift:46` 的 `subscript(offset:)` 用 `precondition`，越界即崩，且下标无法加前缀。

**三个方向供选**：

| 方案 | 做法 | 消除什么 | 遗留什么 | 破坏面 |
|---|---|---|---|---|
| **A. 收敛进 `.fdy`** | 运算符/下标全部改为 `.fdy` 命名空间方法（`fdy_add` / `fdy_scaled` / `fdy_merging`），删运算符与无前缀 init | 100% 命名空间污染 | 调用风格变啰嗦 | **最大**：所有调用点编译失败 |
| **B. 加前缀** | 运算符改 `fdy_+`、init 加 `fdy_` 标签 | 撞名风险基本消除 | 仍占全局符号名，风格怪 | 大 |
| **C. 只治理高风险子集** | 只删 `Dictionary`/`String`/`NSPredicate`/`Optional ==` 等「宿主高频自建」的，保留 CG 几何运算 | 风险最高的一批 | 仍有污染 | 中 |

**倾向 C → 再推 A**：先掐掉撞名概率最高的（容器运算符、自定义运算符、无前缀 init），
几何运算类留下（`.fdy` 化会显著伤可读性）。

### 8.1 「加前缀」为什么做不了（编译器实测）

Swift 语法规定**运算符标识符不能含字母或下划线**。三个最小样例实测：

| 写法 | 结果 |
|---|---|
| `infix operator fdy_+` | ✘ `error: 'fdy_' is considered an identifier and must not appear within an operator name` |
| `infix operator +fdy` | ✘ `error: 'fdy' is considered an identifier and must not appear within an operator name` |
| `infix operator <+>` | ✔ 通过（纯符号才合法） |

所以运算符只有两条命运：**保留** 或 **删除后改为 `fdy_` 前缀的具名方法**（后者就是方案 A 的手段）。
方案 B 的一半仍可执行 —— **`init` / `subscript` 加前缀是合法的**，不受此限制。

**大人的裁决：走 B1-a**（运算符全删 → 具名方法；`init` / `subscript` 加前缀），不取「B1-b 只加 init 前缀」的折中。
理由：既然目的是「宿主或三方库同名即编译失败」这个**头号阻塞**被彻底消除，就不该只消除一半 —— 几何运算的可读性损失换 100% 的符号面收敛，值。

| 编号 | 做法 | 消除污染 | 破坏面 | 裁定 |
|---|---|---|---|---|
| **B1-a** | 运算符全删 → 改具名方法（`fdy_adding(_:)` / `fdy_scaled(by:)` / `fdy_merging(_:)`…），同时 `init`/`subscript` 加前缀 | **100%** | 所有调用点需改写 | ✅ **已执行**，见 §8.2 |
| B1-b | 只给 `init`/`subscript` 加前缀，运算符全部保留 | 约 52 处 | 几何运算可读性不受影响 | 未采纳 |
| B1-c | 维持现状 | 0 | 宿主撞名时需自行规避 | 未采纳 |

#### ① 换路径：从私有 `_targets` 取 target，正向调其 action

`_setState:` 走的是低层 state setter，不经过 target-action 派发。而 `UIView+Combine.swift` 的
`fdy_event(_:)` 本质就是一次普通的 `recognizer.addTarget(target, action: #selector(ClosureTarget.invoke(_:)))`。
所以只要**把注册进去的那对 `(target, action)` 取出来正向调用**，就等价于 UIKit 自己的派发路径。

`UIGestureRecognizer` 没有公开的 targets API，但私有 ivar `_targets` 是 `NSMutableArray`
（本轮实测 `ivar_getTypeEncoding` = `@"NSMutableArray"` —— **对象类型，故 KVC 取值安全**，
不会像非对象类型那样在 `value(forKey:)` 上崩）：

```swift
func dispatchTargets(of recognizer: UIGestureRecognizer?) -> (String, Int) {
    guard let recognizer, let targets = recognizer.value(forKey: "targets") as? NSMutableArray else {
        return ("nil", 0)
    }
    var dispatched = 0
    for case let item as NSObject in targets {
        guard let target = item.value(forKey: "target") as? NSObject else { continue }
        if target.responds(to: NSSelectorFromString("invoke:")) {
            _ = target.perform(NSSelectorFromString("invoke:"), with: recognizer)
            dispatched += 1
        } else if target.responds(to: NSSelectorFromString("invoke")) {
            _ = target.perform(NSSelectorFromString("invoke"))
            dispatched += 1
        }
    }
    return ("\(dispatched)/\(targets.count)", dispatched)
}
```

> `ClosureTarget.invoke` 的签名是 `@objc func invoke(_ sender: Any)`（**带参**，故 selector 为 `invoke:`）；
> 对照用的 `ProbeGestureTarget.invoke()` 无参。两个名字都试，靠 `responds(to:)` 兜住 —— 不是猜的。

### 已排除的排查方向（别再跑）

- `swiftc` 整模块 typecheck **抓不出**漏登记 conformance —— 必须走附录 ③。
- 按「`Base ==` 约束即值类型」模式匹配会**误判**（`UIImage.SymbolConfiguration` 是 NSObject 子类）。
  **以编译器为准。**
- **量化命令用 `\s` 一律不可信** —— macOS BSD grep 不支持，静默返回 0。用 `[[:space:]]`。
- **跨模块探针报满屏 `cannot find type` 时先看有没有 `import Fdy`**，不要当成 API 不可达。
- **`simctl launch --console-pty` 对常驻 app 会挂死** —— 不是构建失败，是它不退出。用后台 + 定时 kill。
- 用 `init[?(]fdy_` 这类**单行**模式清点 init 会漏掉 `init?(...)` 与换行的 `convenience init(`，必须人工补扫。
- **`grep -c 'warning:'` 会把诊断的缩进附注行一起数进去** —— 4 条主诊断数成 8。判基线漂移必须看去重后的主诊断。
- **macOS BSD grep 的 BRE 不支持 `\|`**：`grep -n 'a\|b'`（不带 `-E`）**静默当字面量**并返回空，
  与 `\s` 陷阱同源。README 里 `UIColor(hex:)` 漏改就是被它骗过去的。**一律 `grep -E`。**
- **搜不到 ≠ 不存在**：`open class func` 不会被 `static func` 的 grep 模式匹配到。
- **`Edit` 工具偶发静默失效**（报成功但文件未变）—— 本轮 `UIDevice++` 与 README 各中一次。**改完必须回读复核。**
- **CF 类型不需要逐条登记 conformance**：给 `CGPath` 登记后子类 `CGMutablePath` 自动继承，
  原 `CGMutablePath+Chain.swift` 的声明反成重复（编译器 warning 而非 error 报出来）。
  与 `NSObject` 的类继承同一机制，别信「CF 类型必须逐条登记」。
- **`/tmp` 会被系统整体清空** —— 本轮 09:04 前后历史探针全数蒸发。探针一律放 `.build/structprobe/`。
